# Rules Page — Design

**Date:** 2026-09-14
**Status:** Awaiting review
**Route:** `/rules`

## Goal

Make the BouseInTheNose Master Rulebook readable and searchable on the site:
collapsible chapter containers, smooth expansion, and a search that finds the
right rule fast for a mid-argument check-up.

## Source Data

`BouseInTheNose_Master_Rulebook Final.docx` (75 KB, ~82 KB of text).

Word styles map cleanly onto the content model:

| Style | Count | Meaning |
|---|---|---|
| `Tittel` | 1 | Document title |
| `Overskrift1` | 21 | Chapter / section heading |
| `Overskrift2` | 143 | Rule heading, e.g. `7.3 Trade Deadline` |
| `Normal` | 523 | Body paragraph |
| `Punktliste` | 31 | Bullet item |

All 143 rule headings begin with a parseable ID (`G.1`, `7.3`, `17.8`, `A.1`).

**Two sections are not chapters of rules:**

- `Contents` — a table of contents. Redundant with site navigation. **Dropped.**
- `Definitions and Terminology` — 19 flat paragraphs with no `Overskrift2`
  headings, each of the form `Term: definition`. Split on the first colon and
  rendered as a **glossary**, not a rule list. All 19 confirmed to contain a
  colon; a paragraph without one is a validation failure.

Rules per chapter: General Provisions 8, Ch1 7, Ch2 6, Ch3 8, Ch4 11, Ch5 7,
Ch6 8, Ch7 11, Ch8 5, Ch9 7, Ch10 10, Ch11 9, Ch12 8, Ch13 9, Ch14 6, Ch15 7,
Ch16 5, Ch17 8, Appendix A 3.

**Six paragraphs precede the first heading** (front matter):

```
LEAGUE RULES
BouseInTheNose Fantasy Football League Master Rulebook      [Tittel]
Consolidated draft for final review · 10 September 2026
Season of applicability: [TO CONFIRM]
Adoption date and official version: [TO CONFIRM]
This document consolidates the chapter drafts ...
```

These belong to no chapter. The converter collects them into `frontMatter` and
the page renders them as a header block above the chapter list. Unresolved
`[TO CONFIRM]` values are shown verbatim rather than hidden — the rulebook is
still a draft and the gaps are real.

## Architecture

```
.docx  ──npm run rules──▶  rules.json  ──import──▶  /rules page
(master)                   (generated)              (client search)
```

The .docx stays the single source of truth. `rules.json` is a **derived
artifact**: regenerated by one command, committed for build reproducibility,
never hand-edited. Chapter 12 of the rulebook governs amendments, so the
document is expected to change; re-import must be one step.

### Data model

```ts
type Rule = {
  id: string          // "7.3"  — stable, used as the URL anchor
  title: string       // "Trade Deadline"
  body: string[]      // paragraphs
  bullets: string[]   // list items
}

type Chapter = {
  id: string          // "ch-7"
  number: number | null
  title: string       // "Chapter 7 — Trades"
  kind: "chapter" | "preamble" | "glossary"
  rules: Rule[]
}

type Definition = { term: string; text: string }

type Rulebook = {
  title: string
  generatedAt: string
  frontMatter: string[]
  chapters: Chapter[]
  glossary: Definition[]
}
```

## Components

```
scripts/build-rules.mjs        docx → rules.json (Node, dev only)
app/data/rules.json            generated
app/rules/page.tsx             server component, imports json
app/rules/RulesBrowser.tsx     client — owns all interactive state
app/rules/ChapterPanel.tsx     one collapsible container
app/rules/RuleCard.tsx         one rule, with copy-link
app/rules/search.ts            MiniSearch index + query helpers
app/rules/highlight.ts         highlightSegments()
```

State is owned solely by `RulesBrowser` (`query`, `openChapters: Set<string>`).
Children are pure and prop-driven. Search must be able to force chapters open,
so a single owner prevents two components disagreeing about the same truth.

## Search

MiniSearch, client-side. The whole corpus is ~82 KB; no server or API involved.

```ts
new MiniSearch({
  fields: ["id", "title", "text"],
  storeFields: ["chapterId", "ruleId"],
  searchOptions: {
    boost: { id: 5, title: 3, text: 1 },
    prefix: (t) => t.length > 2,
    fuzzy:  (t) => (t.length > 3 ? 0.2 : false),
    combineWith: "AND",
  },
})
```

**Why MiniSearch over `includes()` or Fuse.js:** an inverted index with BM25
ranking surfaces the *most relevant* rule rather than the first one in document
order. BM25 also weights rare terms above common ones — "Decathlon" (3 rules) is
a stronger signal than "Commissioner" (60 rules). Fuse.js scores every string on
every keystroke and is tuned for short strings; on 523 paragraphs of prose its
fuzzy matching produces noise ("trade" matching "grade").

Prefix and fuzzy are guarded by term length: applying fuzzy matching to two-letter
terms makes everything match everything.

Index is built once with `useMemo` on mount, not per keystroke.

## Interaction

### Browsing (no query)

All chapters collapsed on load, showing the rulebook's full shape on one screen.
Multiple chapters may be open at once; opening one never closes another —
cross-references between chapters are common, so comparison must be possible.

### Searching

```
query empty  →  all collapsed, nothing filtered, previous open-set restored
query typed  →  non-matching chapters hidden entirely
                matching chapters force-open
                matched terms highlighted in title and body
                header shows "N rules in M chapters"
no results   →  empty state naming the query
```

### Expansion animation

`height: auto` is not animatable. `max-height` hacks animate toward a fake value,
so short rules snap and long ones lag. Measuring `scrollHeight` in JS forces a
reflow on every toggle and breaks on resize.

Use CSS grid instead:

```css
.panel      { display: grid; grid-template-rows: 0fr;
              transition: grid-template-rows 280ms cubic-bezier(.4,0,.2,1); }
.panel.open { grid-template-rows: 1fr; }
.panel > div { overflow: hidden; }
```

True auto height, pure CSS, resize-safe.

The chapter header is the collapse control and becomes `position: sticky` while
open, so closing a long chapter never requires scrolling back to the top.

Respect `prefers-reduced-motion`: transition duration drops to 0.

## Highlighting

The user's typed query is not the matched text — prefix and fuzzy matching mean
"waivr" matches "waivers". MiniSearch returns `result.match`, mapping the actual
matched terms to the fields they hit. Highlighting uses those terms.

```
result.match = { waivers: ["text"], deadline: ["title", "text"] }
        │
        ▼
highlightSegments(text, terms) → [{ text: "...", hit: false }, ...]
        │
        ▼
segs.map(s => s.hit ? <mark>{s.text}</mark> : s.text)
```

`highlightSegments` returns **data, not HTML**. React renders the segments, so
`dangerouslySetInnerHTML` is never used and markup injection is structurally
impossible rather than incidentally safe.

Terms are regex-escaped before being combined into the match pattern.

## URL State

`/rules#7.3` expands the containing chapter, scrolls the rule into view and
flash-highlights it. Each rule has a copy-link button.

Read the hash on mount and on `hashchange`. The search query is **not** synced to
the URL (decided: rule links are the shareable unit; query sync adds state
juggling for little gain).

## Error Handling

The converter parses a third-party XML format, so it validates and fails loudly:

- rule count matches expectation
- every rule ID matches `/^([A-Z]\.)?\d+(\.\d+)*$/`
- no rule has an empty body
- no rule appears outside a chapter (front matter is collected, not an error)
- exactly one glossary section, exactly one dropped TOC

A validation failure exits non-zero and writes nothing. A partially-correct
`rules.json` is worse than no update.

Runtime: `rules.json` is imported at build time, so there is no fetch and no
loading or network-error state on the page.

## Testing

The converter carries the risk (parsing someone else's format), so it gets real
coverage:

- 143 rules across 19 chapters
- every ID parses; IDs are unique
- glossary extracted with 19 definitions
- TOC dropped
- front matter collected (6 paragraphs), not treated as rules
- bullets attach to the correct rule
- malformed input fails loudly rather than emitting partial output

Search and highlight:

- `"waivr"` returns the waivers rule (fuzzy)
- `"waiv"` returns it (prefix)
- `"7.3"` ranks rule 7.3 first (id boost)
- `highlightSegments` handles overlapping terms, regex-special characters, and
  no-match passthrough

## Styling

Follows the existing dark/glass treatment from `app/stats/page.tsx`: layered
background gradients, cyan (`#62dfff`) and violet (`#a78bfa`) accents, uppercase
tracked labels, heavy weights.

## Out of Scope

- Print / PDF stylesheet
- Rule change history or amendment diffs
- Editing rules in the browser
- Search query in the URL
